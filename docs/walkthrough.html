    Walkthrough: send & store

    Build the complete loop a contract takes through your app: a form uploads the PDF, a controller sends it in signing order, Adobe calls your webhook when everyone has signed, and a queued job saves the signed PDF to your storage. Every class is complete and copy-pasteable.

    The loop at a glance

    The code below comes from the package's examples/ directory. It isn't just illustration: the package's test suite (SigningLifecycleTest) runs these exact classes end to end against a fake Acrobat Sign, from the form upload to the PDF landing in storage.

    The split matters. Adobe gives a webhook 5 seconds to answer, and a signed PDF with its audit report can take longer than that to download. So the webhook route only acknowledges and fires an event, the listener runs on the queue, and the heavy work happens in a job that can retry on its own schedule.

    Before you start

    • The package is installed and php artisan adobe-sign:verify succeeds (Installation).
    • APP_URL is a public HTTPS address. Locally that means a tunnel; see local development. Adobe only calls HTTPS URLs, and WebhookInfo rejects anything else before sending.
    • ADOBE_SIGN_WEBHOOK_CLIENT_IDS (or ADOBE_SIGN_CLIENT_ID) holds the client id Adobe will send, so the route accepts the callbacks.
    • A queue connection other than sync, and a worker running: php artisan queue:work.
    • A user to sign as. In a developer account, send to addresses you control; Adobe marks the agreements as demo documents.

    Step 1: Routes

    Your app needs routes for its own controller. The package registers the webhook route (adobe-sign.webhook) itself, so it doesn't appear here.

    In a standard app routes/web.php already has the web group; listing it explicitly does no harm and matches the example file.

    Step 2: The upload form

    A plain multipart form: the PDF, a name, the signers in signing order, and a way to mark a signer as signing at the same step as the one before them.

    With the box ticked, Jane and legal sign in parallel at step 1 and the CEO signs at step 2.

    Step 3: The controller

    The controller validates the request, uploads the PDF, builds the signing order, creates the agreement and registers a webhook for it. It receives the client by injection, so it works with whichever auth mode you configured.

    What each part of store() does

    1. Validation before anything leaves your app

      mimes:pdf and max:25600 (25 MB) reject bad uploads with a normal 422, and no request reaches Adobe. The package's test suite checks exactly that.

    2. Upload as a transient document

      The upload is streamed through a temporary file, so memory use stays flat for large PDFs. The original file name and MIME type are passed because the temporary path has no extension.

    3. Turn the form into a signing order

      The loop gives each signer the next order number, unless they appear in parallel[], in which case they reuse the current number. With the form above the result is Jane 1, legal 1, CEO 2. The builder checks that the numbers run 1..n without gaps before sending anything.

    4. Create, which also sends

      agreements()->create() returns the new agreement id. Its default state, IN_PROCESS, means Adobe emails the first step's signers immediately. The project's signature level from ADOBE_SIGN_SIGNATURE_LEVEL is applied here too.

    5. Register a webhook for this agreement

      route('adobe-sign.webhook') builds the public URL of the package's route from APP_URL or the current request. Adobe verifies that URL immediately by calling it, and the package answers the handshake, so this call only succeeds when your app is reachable. One webhook per agreement is Adobe's recommendation: if deliveries keep failing, Adobe disables only that webhook.

    Keep a record on your side

    The example returns the agreement id as JSON. In a real app, store it on your own model (say contracts.adobe_agreement_id) and set ->externalId((string) $contract->id) on the builder, so both systems can find each other. See Create and send an agreement.

    Step 4: The webhook route (already done)

    You don't write this part. When the last signer finishes, Adobe sends a POST to /adobe-sign/webhook with an X-AdobeSign-ClientId header and a JSON body whose event is AGREEMENT_WORKFLOW_COMPLETED. The package's WebhookController:

    1. rejects the call with 403 if the client id isn't on your allow-list;
    2. parses the body into a typed event (AgreementEvent here), or answers 400 if it can't;
    3. adds the notification id to the cache, and only fires WebhookReceived if it wasn't there already;
    4. answers 200 with the client id echoed in a header and the JSON body, which is how Adobe knows the delivery succeeded.

    All of that takes milliseconds, well inside Adobe's 5 seconds, provided your listeners are queued. Details on the Webhooks page.

    Step 5: The queued listener

    The listener decides what each event means for your app. It implements ShouldQueue, so Laravel serialises the event onto the queue and the webhook request returns straight away.

    Laravel 11 and later discover listeners in app/Listeners from the type-hint on handle(). If you turned discovery off, register it in a service provider: 

    use App\Listeners\ProcessAdobeSignWebhook;
use Conceptlz\AdobeSign\Laravel\Events\WebhookReceived;
use Illuminate\Support\Facades\Event;

Event::listen(WebhookReceived::class, ProcessAdobeSignWebhook::class);

    AGREEMENT_ALL subscribes to every agreement event, so the listener also sees views, reminders and individual signatures. The match makes the interesting ones explicit and ignores the rest. The null arms are where you'd update your own records, e.g. mark the contract as declined.

    Step 6: The download job

    The job does the slow, fallible part, with its own retry budget. It is the only place that touches Adobe after signing.

    Why the job is written this way

    • It re-checks the status. Adobe doesn't sign webhook payloads. The client-id allow-list stops casual forgeries, but the safe pattern is to treat the webhook as a hint and ask the API for the truth. Only a real SIGNED status leads to a download.
    • It asks for the audit report. attachAuditReport: true appends Adobe's audit trail (who signed, when, from which IP, with which verification) to the PDF. Keep it with the document: it is what you show when a signature is challenged.
    • It streams. combinedDocument() returns a PSR-7 stream; detach() hands its underlying PHP resource to Storage::writeStream(), which copies it to local disk, S3 or any other driver in chunks.
    • It cooperates with throttling. Short Retry-After waits are retried inside the SDK. A long one surfaces as RateLimitException, and the job puts itself back on the queue for that many seconds instead of burning a try.
    • It injects the default client. That is right for an Integration Key. With OAuth there is no signed-in user in a worker, so pass the user key into the job and use AdobeSignManager::forUser(); see queued jobs.

    Step 7: Try it

    1. Start a worker 
      php artisan queue:work
    2. Submit the form

      Signed in to your app, upload a PDF with two or three addresses you control. The response contains the agreement id, and the first signers receive an email from Acrobat Sign.

    3. Watch progress

      Open /agreements/{id} to see the status move from OUT_FOR_SIGNATURE to SIGNED. Each signature also produces an AGREEMENT_ACTION_COMPLETED line in your log from the listener.

    4. Find the signed PDF

      After the last signature, the worker runs the listener, then the job, and storage/app/agreements/{id}.pdf (or the same path on your default disk) appears, with the audit report on its last pages.

    Step 8: Test it without Adobe

    The package's own SigningLifecycleTest runs this whole loop with a fake HTTP client and the sync queue: it posts the form, checks the upload body, the signing order and the webhook URL, posts Adobe's completion webhook to the route, and asserts the PDF is in the faked disk. The Testing page shows how to write the same test in your app.

    Hardening for production

    • Idempotency. The package drops duplicate deliveries for 72 hours, but a job can still run twice (a retry after a timeout, a manual replay). Writing the same file twice is harmless here; if the job also sends emails or bills, check your own record first or use ShouldBeUnique keyed on the agreement id.
    • Failure handling. Add a failed() method to the job that flags the contract for attention. After 72 hours of failed webhook deliveries Adobe disables the webhook, so a scheduled sweep that checks agreements still marked "sent" is a cheap safety net.
    • Timeouts. Large agreements with many pages can take a while to download. Give the job a $timeout that fits, and make sure your HTTP client timeout (see the HTTP client) is shorter than the job timeout.
    • Storage layout. Store under a path you control (agreements/{year}/{id}.pdf) and keep the agreement id on your model. Adobe also keeps the document, but your retention rules may differ from theirs.
    • Signature level. If the project requires AES or QES, check it in the job before marking the contract complete: AdobeSign::signatureShortfalls($this->agreementId). See checking after signing.

    Common questions

    webhooks()->create() fails while creating the agreement works. Why?

    Adobe calls your URL to verify it before creating the webhook. It must be public HTTPS, reach the package route without auth or CSRF middleware, and your allow-list must contain the client id Adobe sends. Locally you need a tunnel. See Troubleshooting.

    Everyone signed, but no PDF appeared in storage. Where do I look?

    Check, in order: that a queue worker is running (the listener and job are both queued), the failed_jobs table, your log for "Rejected Acrobat Sign webhook" warnings, and the webhook's status in Acrobat Sign. More in Troubleshooting.

    Can I use one account-wide webhook instead of one per agreement?

    Yes: create it once with WebhookInfo::forAccount('All agreements', route('adobe-sign.webhook')) (an admin task) and drop step 4 of the controller. Adobe recommends per-agreement webhooks because a disabled webhook then affects one agreement, not all of them.

    How does this change if users send from their own accounts via OAuth?

    In the controller, use AdobeSign::forUser($request->user()) instead of the injected client. In the listener, look up which user owns the agreement (from your own records) and pass that user's key into the job, which calls forUser($key). The webhook route itself needs no change. See OAuth.

    Can I store the audit report as a separate file?

    Yes. Call combinedDocument($id) without attachAuditReport for the signed PDF and auditTrail($id) for the report, and write each stream to its own path. The core's downloads page lists the other formats.
